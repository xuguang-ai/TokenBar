# Phase 0 — Feasibility findings (condensed)

Source: Phase 0 research workflow on 2026-10-05 (3 research agents and 2 adversarial verifiers). The verifier corrections override the original claims. Emails and account ids are redacted.


## Claude

### Summary

GO (for Claude side). A third-party macOS app can read Claude Code usage for multiple accounts entirely from local sources, without opening a web page or re-logging in. Two viable data paths were confirmed by decompiling the installed native binaries (npm CLI 2.1.123 and the newer VS Code-bundled 2.1.289) and by running the read-only `claude auth status`. (A) Identity + live rate-limit utilization is already cached on disk in the global config JSON (`cachedUsageUtilization`, written from `anthropic-ratelimit-unified-*` response headers) — fully readable with no network and no secret handling. (B) Exact plan usage (5h / 7d windows + reset times) comes from `GET https://api.anthropic.com/api/oauth/usage` with `Authorization: Bearer <accessToken>` + `anthropic-beta: oauth-2025-04-20`, where the access token lives in a macOS Keychain generic-password item created via `/usr/bin/security`. Multiple accounts are isolated by launching each Claude Code with a distinct `CLAUDE_CONFIG_DIR`; the Keychain service name is `Claude Code-credentials` (default) or `Claude Code-credentials-<sha256(NFC(configDir))[:8]>` when `CLAUDE_CONFIG_DIR` is set. Token-refresh coordination is the main risk: refresh tokens can rotate, so an uncoordinated refresh by TokenBar could log Claude Code out — the recommendation is to read only and never refresh. NOTE: per the hard rules I did not run `security` or touch the Keychain, so the actual no-prompt readability of the item is an open question to verify in Phase 0 spike code.

### Recommended approach

Build the Claude provider as READ-ONLY, preferring the on-disk cache and shelling out to /usr/bin/security for the token; never call the OAuth refresh endpoint.

Per Claude account, the user configures a distinct CLAUDE_CONFIG_DIR (e.g. ~/.claude-work, ~/.claude-personal) and signs in to Claude Code once in each. TokenBar stores only that configDir string per account (non-secret).

Read path per account (fast, no network, <1s, satisfies success criteria):
1. Resolve globalConfig = join(CLAUDE_CONFIG_DIR, '.claude.json') (or ~/.claude.json when the account is the default/unset one). Read JSON.
2. Identity: globalConfig.oauthAccount.{emailAddress, organizationName, organizationType, organizationRateLimitTier, accountUuid}. organizationType maps claude_max→max/claude_pro→pro/etc.
3. Live-ish usage WITHOUT any secret or network: globalConfig.cachedUsageUtilization = { fetchedAtMs, accountUuid, utilization:{ five_hour:{utilization,resets_at}, seven_day:{...}, seven_day_sonnet, limits:[...], extra_usage } }. Here utilization is 0-100 and resets_at is ISO-8601 (epoch-seconds on some model-scoped rows). This is written by Claude Code from inference-response headers and persisted (max age 1h in CC's own reader). Show it with a 'last updated' stamp — exactly the card TokenBar wants, and zero credential handling.

Authoritative usage (optional, for freshness when CC hasn't run recently):
4. Derive Keychain service name (see artifact) and read the token via `/usr/bin/security find-generic-password -a "$USER" -w -s "<service>"`. The item was created by /usr/bin/security, so /usr/bin/security should read it back without a GUI prompt (VERIFY in a spike — I was blocked from testing). Parse claudeAiOauth.{accessToken, expiresAt}.
5. If Date.now() < expiresAt-5min, GET https://api.anthropic.com/api/oauth/usage with headers Authorization: Bearer <accessToken>, anthropic-beta: oauth-2025-04-20, Content-Type: application/json, User-Agent: TokenBar/x. Parse five_hour/seven_day/seven_day_sonnet/extra_usage/limits (utilization 0-100). Requires the token to carry scope user:profile (Claude Code tokens do).
6. If the token is expired, DO NOT refresh. Fall back to cachedUsageUtilization and show stale + 'Unable to refresh'. Claude Code refreshes its own token on its next activity/startup; TokenBar piggybacks on that.

Prefer step 3 as the default data source and treat step 5 as an opportunistic enhancement. This keeps credentials on the machine (token only read, never written/uploaded), avoids the refresh-rotation hazard entirely, and needs no re-login.

Reuse the same two-tier pattern (cache file first, Keychain+HTTP second) as the UsageProvider contract so Codex slots in identically.

### Findings

- **keychain.service-name** (high) — verifier: **confirmed**: The macOS Keychain generic-password SERVICE name is `Claude Code` + OAUTH_FILE_SUFFIX + `-credentials` + (CLAUDE_CONFIG_DIR set ? `-`+sha256hex[:8] : ''). Prod OAUTH_FILE_SUFFIX is empty, so default = `Claude Code-credentials`.
- **keychain.service-name.hash-input** (high) — verifier: **confirmed**: The sha256 input is the resolved config dir, NFC-normalized, used RAW: no realpath, no symlink resolution, trailing slash NOT stripped. When CLAUDE_SECURESTORAGE_CONFIG_DIR is unset (normal), the switch is `!process.env.CLAUDE_CONFIG_DIR` and the input is `we()` = `(CLAUDE_CONFIG_DIR ?? join(home,'.claude')).normalize('NFC')`. Truncation = first 8 hex chars of the hex digest.
- **keychain.account-attribute** (high) — verifier: **confirmed**: The account attribute (-a) is the OS username: process.env.USER or userInfo().username, validated against /^[a-zA-Z0-9._-]+$/, falling back to the literal `claude-code-user`. It is the SAME for every account on the machine — accounts are distinguished by the service name, not the account.
- **keychain.read-write-mechanism** (high) — verifier: **confirmed**: Claude Code reads/writes the Keychain by spawning /usr/bin/security (not the Security.framework API). Read: `security find-generic-password -a "<user>" -w -s "<service>"`. Write: `add-generic-password -U -a <user> -s <service> -X <hexJSON>` piped to `security -i` on stdin (argv form if the stdin line would exceed 4032 bytes). Delete: `security delete-generic-password -a <user> -s <service>`. Because the item is created by /usr/bin/security, another process calling /usr/bin/security can read it back without a GUI prompt.
- **keychain.exit-codes** (high) — verifier: **confirmed**: Claude Code interprets security exit codes: 44 = item-not-found (treated as null/no credential), 36 = inaccessible/interaction-not-allowed (keychain locked). TokenBar should treat 44 as 'account not signed in' and 36 as 'keychain locked, retry'.
- **credentials.plaintext-fallback** (high) — verifier: **confirmed**: On macOS the Keychain is the primary store; a plaintext file `<configDir>/.credentials.json` (mode 0600) is used only as a fallback when the Keychain write fails. Storage is `Gn()=x(P,T)` (keychain P with plaintext T fallback). Writing plaintext logs `Warning: Storing credentials in plaintext.`
- **credentials.schema** (high) — verifier: **confirmed**: The credential blob (both keychain value and .credentials.json) is JSON keyed `claudeAiOauth`: {accessToken:string, refreshToken:string, expiresAt:number(epoch ms), refreshTokenExpiresAt?:number, scopes:string[], subscriptionType:'max'|'pro'|'enterprise'|'team'|null, rateLimitTier:string|null, clientId?:string}. expiresAt = Date.now()+expires_in*1000. Other sibling secret keys in the same store include mcpOAuth, pluginSecrets, trustedDeviceToken.
- **config.dir-resolution** (high) — verifier: **confirmed**: Config dir default is ~/.claude; override is CLAUDE_CONFIG_DIR (resolved then NFC-normalized). An additional CLAUDE_SECURESTORAGE_CONFIG_DIR can override only the credential-storage dir (new in 2.1.289).
- **config.global-json-path** (high) — verifier: **confirmed**: The global config JSON is `<configDir>/.config.json` if it exists, else `join(CLAUDE_CONFIG_DIR || homedir(), '.claude.json')` (prod suffix empty). So: ~/.claude.json when CLAUDE_CONFIG_DIR is unset; <CLAUDE_CONFIG_DIR>/.claude.json when set. This file holds oauthAccount and (critically) cachedUsageUtilization.
- **config.oauthAccount-fields** (high) — verifier: **confirmed**: globalConfig.oauthAccount (non-secret identity) contains: accountUuid, emailAddress, organizationUuid, organizationName, organizationType, organizationRole, workspaceRole, organizationRateLimitTier, userRateLimitTier, seatTier, hasExtraUsageEnabled, billingType, accountCreatedAt, subscriptionCreatedAt, displayName, fullName, profileFetchedAt, ccOnboardingFlags, claudeCodeTrialEndsAt, claudeCodeTrialDurationDays.
- **config.cachedUsageUtilization** (high) — verifier: **refuted**: KEY FINDING for TokenBar: Claude Code persists the latest usage utilization to globalConfig.cachedUsageUtilization = {fetchedAtMs, accountUuid?, utilization:{five_hour, seven_day, seven_day_oauth_apps, seven_day_opus, seven_day_sonnet, cinder_cove, extra_usage, limits[]}}. Each window = {utilization:number|null, resets_at:string|null}. This lets TokenBar show 5h/7d % and reset times with NO network and NO secret access. CC's own reader treats it valid up to 1h old (bvn=3600000) and only serves it if accountUuid matches.
  - **Correction:** The schema and the accountUuid guard are right. The rest is not. The value is not a continuously updated 'latest utilization' and is not written from inference headers. It is a snapshot of the last successful /api/oauth/usage body, written at most once per 60 s, and only when something performs a usage read. Those triggers are the /usage screen, `claude -p /usage`, and SDK get_usage; the VS Code extension sends get_usage after login, on its first config probe, and when its panel asks. On this machine the terminal CLIs never write it (PATH resolves to 2.1.123, plus native 2.1.174). CC trusts the cache for 60 s or less to skip the network, and for up to 1 h only as an error fallback. It is cleared on logout and when the account changes. It is an opportunistic, often stale source, not a reliable default.
- **usage.endpoint** (high) — verifier: **confirmed**: The /usage screen's plan data comes from `GET https://api.anthropic.com/api/oauth/usage` (BASE_API_URL=https://api.anthropic.com). Query variants exist: `?at_wall=1&skip_spend=1` and `?cedar_ember=1&skip_spend=1`; the plain form is used for the usage card. Timeout 5000ms, validateStatus 200-299.
- **usage.headers** (high) — verifier: **confirmed**: Required request headers for /api/oauth/usage (claude-ai-oauth auth): Authorization: Bearer <accessToken>; anthropic-beta: oauth-2025-04-20; User-Agent: claude-cli/2.1.289 (external, cli) (any UA works in practice); Content-Type: application/json. No anthropic-version header is sent on this call.
- **usage.scope-required** (high) — verifier: **confirmed**: Fetching /api/oauth/usage requires the OAuth token to carry scope `user:profile` (M4). Claude Code gates the fetch on Zp() = scopes.includes('user:profile') AND ft() = has inference scope. Claude Code login tokens include user:profile by default.
- **usage.schema** (high) — verifier: **confirmed**: Response JSON (2.1.289) top-level keys: five_hour, seven_day, seven_day_opus, seven_day_sonnet, seven_day_oauth_apps, cinder_cove, extra_usage, limits. Each window object = {utilization:number|null, resets_at:string|null}. extra_usage = {is_enabled:bool, monthly_limit:number|null, used_credits:number|null, utilization:number|null, currency:string|null, disabled_reason?:string|null} (amounts in cents). limits[] rows = {kind, group, percent, resets_at, severity, is_active, scope:{model:{display_name}|null, surface:{display_name}|null}}.
- **usage.utilization-scale** (high) — verifier: **confirmed**: In the /api/oauth/usage JSON body, utilization and limits[].percent are WHOLE PERCENTS 0-100 (can exceed 100 when over). resets_at in the body is an ISO-8601 string for top-level windows; some model-scoped limit rows carry epoch-SECONDS numbers (code branches on typeof==='number'). By contrast the inference-response rate-limit HEADERS use a 0-1 FRACTION and epoch-seconds resets. CC multiplies header fractions by 100 to match the body scale.
- **usage.ui-labels** (high) — verifier: **confirmed**: The /usage UI labels each bucket: five_hour='Current session'; seven_day='Current week (all models)'; seven_day_sonnet='Current week (Sonnet only)' (shown when plan is max/team/unknown); model-scoped limits='Current week (<model display_name>)'; cinder_cove='Claude Code and Cowork credit' (one-time credit); extra_usage='Usage credits'.
- **refresh.endpoint** (high) — verifier: **confirmed**: OAuth token refresh: POST https://platform.claude.com/v1/oauth/token, body {grant_type:'refresh_token', refresh_token, client_id, scope:'<space-joined>'}, Content-Type application/json, timeout 30s. client_id (prod) = <uuid>. Revoke: POST <TOKEN_URL>/revoke.
- **refresh.rotation-risk** (high) — verifier: **confirmed**: Refresh tokens CAN rotate: the stored refreshToken becomes the server's returned refresh_token (falling back to the old one only if absent): `refresh_token:K=e`. If a third party refreshes and the server rotates, Claude Code's on-disk refresh token goes stale; on its next refresh CC gets invalid_grant and CLEARS its stored tokens (accessToken/refreshToken emptied), logging the user out. Therefore TokenBar must NOT refresh.
- **refresh.expiry-threshold** (high) — verifier: **confirmed**: Claude Code considers a token expired/refreshable when within 5 minutes of expiresAt: KF(e)= `Date.now()+300000>=e`. TokenBar should use the same 5-minute margin to decide whether the cached accessToken is still usable before calling the usage endpoint.
- **refresh.lock-protocol** (high) — verifier: **confirmed**: Refresh is serialized cross-process by a directory lock `<configDir>/.oauth_refresh.lock` (proper-lockfile: mkdir-based, stale=60000ms, update=5000ms) plus a legacy `<path>.lock` and an owner-record file `<configDir>/.oauth_refresh.lock.owner` (JSON {pid,procStart,pidDomain,pidSpace,lockBirthtimeMs,legacyLockBirthtimeMs}) enabling dead-holder takeover. The stray `.oauth_refresh.lock.owner.tmp.<8hex>` on disk is the atomic-write temp for that owner record.
- **cli.auth-status** (high) — verifier: **confirmed**: `claude auth status` exists, is read-only, defaults to JSON (--json default, --text option). It returns identity only — {loggedIn, authMethod, apiProvider, email, orgId, orgName, subscriptionType} — NOT usage, and does NOT send a model prompt or trigger a token refresh (it reads cached config/in-memory creds). Confirmed by running it: exit 0, no prompt.
- **cli.usage-noninteractive** (high) — verifier: **refuted**: There is NO standalone `claude usage` CLI subcommand (top-level commands: agents, auth, auto-mode, doctor, install, mcp, plugin, setup-token, ultrareview, update). /usage is an interactive slash command; non-interactive structured usage is only available via the SDK/print-mode control request `get_usage` (subtype get_usage, optional skip_behaviors), which returns the same AZt() data (session cost + rate_limits). So TokenBar cannot shell out to a simple `claude usage` one-shot.
  - **Correction:** It is true there is no `claude usage` subcommand. But in 2.1.289, `claude -p "/usage"` runs the local command without a model call. It prints lines like 'Current session: N% used · resets …' and, via R()/UPo, refreshes cachedUsageUtilization. SDK get_usage is the structured route. Neither helps with 2.1.123: its non-interactive /usage prints only a subscription sentence, and it has no get_usage request.
- **ratelimit.headers** (high) — verifier: **confirmed**: Claude Code reads these inference-response headers as a secondary usage signal (prefix anthropic-ratelimit-unified-): 5h-utilization/-reset/-surpassed-threshold, 7d-utilization/-reset/-surpassed-threshold, 7d_oi-* (seven_day_overage_included), status (allowed|allowed_warning|rejected), reset, fallback, representative-claim, overage-status/-reset/-disabled-reason/-scope/-in-use/-utilization/-surpassed-threshold, overage-period(-monthly|-channel)-utilization, upgrade-paths, grace-5h/7d-utilization, slow-*. Header utilization is a 0-1 fraction; reset is epoch seconds.
- **plan.subscription-types** (high) — verifier: **confirmed**: Subscription/plan mapping: organization_type claude_max→'max', claude_pro→'pro', claude_enterprise→'enterprise', claude_team→'team' (else 'Claude API'). rateLimitTier examples default_claude_max_5x / default_claude_max_20x change thresholds. Enterprise can be 'enterprise_usage_based' (seatTier) which differs. extra_usage is overage/credits (monthly_limit & used_credits in cents). This machine's account is max / default_claude_max_5x.
- **multi-account.isolation** (high) — verifier: **confirmed**: Multiple Claude accounts are isolated by distinct CLAUDE_CONFIG_DIR values: each gets its own ~/.claude.json-equivalent (<dir>/.claude.json with its own oauthAccount + cachedUsageUtilization) AND its own Keychain item (service name hashed from the dir). The DEFAULT (CLAUDE_CONFIG_DIR unset) uses the unhashed `Claude Code-credentials` and ~/.claude.json, so at most one account can be the default; every additional account needs an explicit CLAUDE_CONFIG_DIR. The -a (username) is shared across all.
- **version.differences** (high) — verifier: **confirmed**: 2.1.123 (npm) vs 2.1.289 (VS Code): endpoint, TOKEN_URL, client_id, keychain service scheme, account attr, and keychain subprocess mechanism are IDENTICAL. 2.1.289 ADDS: usage fields seven_day_opus/seven_day_oauth_apps/cinder_cove/limits[] (model-scoped); cachedUsageUtilization disk persistence; CLAUDE_SECURESTORAGE_CONFIG_DIR; the .oauth_refresh.lock owner-record + dead-holder takeover (2.1.123 used plain proper-lockfile with no owner file). 2.1.123 usage schema was only five_hour/seven_day/seven_day_sonnet/extra_usage and its header utilization was stored as *100 inline.
- **usage.fetch-gating** (high) — verifier: **refuted**: Before hitting the network, CC first tries an in-memory snapshot (BPo, <60s old) and the persisted cachedUsageUtilization; it only calls the endpoint when those are stale. A 401 triggers one refresh+retry; repeated failures are remembered per-bearer (auth_rejected ~1h, rate_limited with Retry-After) to avoid hammering. TokenBar replicating the read should similarly rate-limit and cache.
  - **Correction:** There is a single pre-network check, and BPo is not in-memory: it is the persisted cachedUsageUtilization, accepted only if under 60 s old and no newer rate-limit headers have been seen. The copy up to 1 h old is used only as a failure fallback, after in-memory header data. Backoff: a 401, or a 403 with an API error body, blocks for 1 h. A 429 or bare 403 waits for Retry-After, else 5 min, capped at 1 h. Backoff is tracked per bearer token and gated by the GrowthBook flag tengu_federated_robin. A 401 gets one forced refresh and retry via P_.

- Missed no-secret live source: Claude Code passes a `rate_limits` object to the user's statusLine command on stdin. It holds five_hour and seven_day, each with used_percentage (0-100) and resets_at (epoch seconds), built from inference headers after each API response. Limits: it only works in terminal TUI sessions (the VS Code panel does not run statusLine), and it only covers 5h/7d. An opt-in TokenBar statusLine wrapper could save this JSON per config dir (the transcript path reveals which dir) and still run any existing statusLine command.

The get_usage response is structured: {session, subscription_type, rate_limits_available, rate_limits{...,model_scoped}, behaviors}. CC holds its own locks and compare-and-swap, so it rotates tokens safely, and it also rewrites cachedUsageUtilization. Costs: spawning a ~220 MB binary, and it is unavailable in 2.1.123.
- Installed builds on this machine: `claude` on PATH resolves first to nvm 2.1.123, then ~/.local/bin/claude (native 2.1.174). VS Code has extension builds 2.1.287 and 2.1.289. Only the VS Code builds can write cachedUsageUtilization; the extension sends get_usage after login, on its first config probe, and when its panel asks. Terminal use here never updates the cache.
- Other Claude Code keychain items TokenBar must not confuse with the OAuth item: 'Claude Code' plus the same hash suffix (legacy /login-managed API key, from x$() with no argument), 'Claude Code-device-keys' (unhashed, device key store, which treats exit codes 37 and 50 specially), and 'Claude Code-doctor-probe' (created and deleted by doctor).

If the keychain returns 44, it should also try <Nb()>/.credentials.json, because CC reads that file in the same case.
- When /api/oauth/usage returns 401, TokenBar should re-read the keychain once rather than refresh; that is what CC's own 401 recovery does when the stored accessToken has changed. It should copy CC's backoff (1 h after a 401 or auth 403; Retry-After, else 5 min, after a 429) and poll no faster than CC's 60 s window.
- Cache lifecycle (2.1.287+): writes happen at most once per 60 s per account. The cache is deleted on logout (TZt resets cachedUsageUtilization) and whenever its accountUuid differs from oauthAccount.accountUuid (eGn). TokenBar should require the two accountUuids to match and display the age of fetchedAtMs.
- Precise lock layout, relevant only if refreshing is ever reconsidered: `<Nb()>/.oauth_refresh.lock` (mkdir, stale 60 s, update 5 s) plus the legacy `<realpath(Nb())>.lock` (e.g. /Users/xai/.claude.lock, used by 2.1.123 with proper-lockfile defaults), the `<Nb()>/.oauth_refresh.lock.owner` record, and `<Nb()>/.storage-write` (stale 15 s, 10 retries). The save is a compare-and-swap on the stored refreshToken. Writing tokens back correctly needs all of these, which is another reason TokenBar should stay read-only.
- Edge case: CLAUDE_CODE_CUSTOM_OAUTH_URL (approved endpoints only) changes OAUTH_FILE_SUFFIX to '-custom-oauth'. The service then becomes 'Claude Code-custom-oauth-credentials[-hash]' and the global config '.claude-custom-oauth.json'. TokenBar may want to detect this env var in user setups.
- Exit codes beyond 44 and 36 are my inference and unverified. `security` appears to exit with the low byte of the OSStatus, e.g. user cancel (-128) gives 128 and auth failed (-25293) gives 51. CC treats every code other than 0, 44 and 36 as READ_FAILED, and WZo() also classifies stderr text (user_canceled, auth_failed, keychain_locked, item_not_found). TokenBar's spike should check which code a denied prompt produces.
- Policy limits on my verification: I did not run `claude auth status`, `security`, or any network call. That `/usr/bin/security` reads Claude Code's item from another process without a prompt, that the server requires user:profile, that any User-Agent works, and that the server rotates refresh tokens all remain unverified. They belong in the Phase 0 spike.

### Risks

- Refresh-token rotation logout: if TokenBar ever POSTs to the OAuth token endpoint with a Claude Code refresh token and the server rotates it, Claude Code's stored refresh token goes stale and CC clears its credentials on the next refresh (invalid_grant), logging the user out. Mitigation: TokenBar must be strictly read-only and never call /v1/oauth/token.
- Keychain GUI prompt not verified: the plan relies on /usr/bin/security reading CC's item without a prompt. This follows from CC creating the item via /usr/bin/security (so security is in the item's trusted-app ACL) and standard macOS behavior, but I was blocked by policy from running security/Keychain, so it is unproven on this machine. A native Swift app that uses SecItemCopyMatching directly (different binary, not in the ACL) would almost certainly trigger a prompt — TokenBar should shell out to /usr/bin/security, not use Security.framework for the read.
- Token staleness when CC is idle: if Claude Code hasn't run recently and its access token is expired, the usage endpoint returns 401 and TokenBar (which must not refresh) can only show cached/last-known usage. Acceptable for an at-a-glance dashboard, but 'fresh on demand' isn't guaranteed without CC activity.
- cachedUsageUtilization can be absent or stale: it's only written after CC observes inference-response headers / fetches usage, is dropped when accountUuid mismatches, and CC's own reader treats it invalid past 1h. A brand-new or long-idle account may have no cache, so TokenBar needs the Keychain+HTTP path as a backstop and must show a 'last updated' timestamp.
- Undocumented/experimental surfaces: the usage endpoint and get_usage SDK request are explicitly marked experimental ('MAY_CHANGE_DO_NOT_RELY_ON_THIS_API_YET'); field names/scales already differ between 2.1.123 and 2.1.289. TokenBar must parse defensively (nullable everything, tolerate new keys, handle utilization as 0-100 in the body but 0-1 in headers).
- Reading ~/.claude.json carelessly leaks secrets: that file also contains MCP server env vars and other secrets. TokenBar must extract only oauthAccount and cachedUsageUtilization, never log or copy the whole file.
- Config-dir hash fragility: the Keychain service hash is computed from the raw NFC config-dir string with no normalization — a trailing slash, symlink, or ~ vs absolute path produces a different hash and a 'not found'. TokenBar must store and reuse the exact string the user ran Claude Code with.
- Concurrent refresh collision if TokenBar ever did refresh: even with the .oauth_refresh.lock, CC's stale/takeover logic (60s stale) could reclaim the lock, so cooperative locking is not a safe substitute for simply not refreshing.

## Codex

### Summary

GO on the Codex side. The official `codex app-server` exposes two stable (non-experimental) v2 methods over JSON-RPC on stdio, one JSON object per line: `account/rateLimits/read` and `account/read`. ### Recommended approach

PRIMARY (MVP): CodexProvider runs the official `codex app-server` per refresh: every 5 minutes, on manual refresh, at launch, and on wake.

1. Spawn `<codex> app-server --listen stdio://`. Use env CODEX_HOME=<account's profile> (default ~/.codex) and RUST_LOG=error. Do not pass --analytics-default-enabled.
2. Send initialize: {"method":"initialize","id":0,"params":{"clientInfo":{"name":"tokenbar","title":"TokenBar","version":"<app version>"},"capabilities":{"experimentalApi":false}}}. Wait for the result and check result.codexHome.
3. Send {"method":"initialized"}.
4. Pipeline {"method":"account/read","id":1,"params":{"refreshToken":false}} and {"method":"account/rateLimits/read","id":2,"params":{"excludeResetCreditDetails":true}}.
5. Match responses by id and ignore notifications. Answer any server-to-client request with error -32601.
6. Close stdin. The server exits with code 0 in about 10 ms. Escalate to SIGTERM after 3 s, then SIGKILL. Use a 20 s overall timeout.

Mapping and display:
- Snapshot = rateLimitsByLimitId["codex"] ?? rateLimits. Decode tolerantly: optional fields, ignore unknown keys.
- Label windows by windowDurationMins (300 = "5h", 10080 = "Weekly"), not by primary/secondary position.
- remaining = 100 - usedPercent. Countdown from resetsAt (unix seconds).
- If usedPercent == 0, show "full / not started" with no ticking countdown, because resetsAt is about now + window and moves.
- rateLimitReachedType non-null, or ordinaryUsageAllowed == false, means Critical.
- Show credits.balance when hasCredits is true.
- account == null, or error -32600 'authentication required', means a "Run `codex login`" state.
- Use account.planType plus a user-chosen display name. Don't show or log the email.
- Allow only three methods: initialize, account/read, account/rateLimits/read. Never call account/rateLimitResetCredit/consume, sendAddCreditsNudgeEmail, login or logout, or account/read with refreshToken:true.
- Codex owns authentication and token refresh. TokenBar never reads auth.json, never sees a token, and stores nothing in the Keychain for Codex.

Why spawn-per-poll: it costs about 0.4–0.75 s, about 0.1 s CPU and about 133 MB for under a second. It always uses the current binary and current auth, and keeps no resident memory. A persistent server with idle shutdown is an optimisation for later.

FALLBACK 1 (instant at launch, offline, or no binary): the passive parse in codex_passive_snapshot.py.
- Read the tail (512 KB) of the newest rollout-*.jsonl files under $CODEX_HOME/sessions and archived_sessions.
- Keep token_count.rate_limits events with limit_id == "codex".
- Keep the newest non-null primary and secondary separately.
- Show as stale ("as of HH:MM"). Treat resets_at <= now as reset (0%).
- Never open Codex's SQLite DBs.

FALLBACK 2 (opt-in only, not for the MVP): call GET https://chatgpt.com/backend-api/wham/usage directly.
- Headers: Authorization: Bearer <tokens.access_token> and ChatGPT-Account-Id: <tokens.account_id>, both read from auth.json.
- Never refresh the token. On a 401, go back to the app-server path. Refresh tokens are single-use, so refreshing would log Codex out.
- This means TokenBar handles a secret, so it should be off by default.

MULTI-ACCOUNT: one CODEX_HOME per Codex account, stored as a per-account setting. Set it up once with `CODEX_HOME=<dir> codex login` and pass it in the spawn environment. GUI apps do not inherit shell variables.

- The App Sandbox is incompatible with this design: running ~/.vscode/... binaries and reading ~/.codex needs a non-sandboxed Developer ID build, so no Mac App Store distribution.
- Every spawn behaves like a Codex launch. It makes startup network calls (at least a models refresh), writes log rows to $CODEX_HOME/logs_2.sqlite, rewrites models_cache.json, and manages $CODEX_HOME/tmp/arg0. Exiting quickly aborted a models-cache write ('failed to write models cache: background task failed'), which is harmless because it is a cache. Keep polls at about 5 minutes or longer, or use a persistent server with idle shutdown.
- Token handling: refresh tokens are single-use ('refresh token was already used ... sign in again'). TokenBar must never refresh tokens or write auth.json itself, and must call account/read with refreshToken:false. The app-server may still refresh tokens as part of normal Codex behaviour; it shares auth.json with the 4 VS Code app-servers already running, and Codex is built for that.
- Calling the wrong method has real consequences: account/rateLimitResetCredit/consume spends a reset credit, sendAddCreditsNudgeEmail sends an email, and logout or login change auth. TokenBar must hard-code a list of allowed methods.
- Passive rollout data is stale and sparse: it only updates while Codex runs turns, windows are often null, and some events are other buckets ('premium'). The latest 5-hour value was 98% but already past its reset. Without the resets_at <= now check it would badly misreport; it can also miss usage from other devices (weekly was 15% passive vs 16% live).
- When a window is unused (usedPercent 0), resetsAt is about now + window and moves on every poll. A naive countdown would show a constant 5h00m.
- GUI apps launched by launchd don't inherit shell PATH or CODEX_HOME. If either is set only in the shell profile, TokenBar needs settings or a one-time login-shell lookup.
- The account email and ChatGPT account ID are personal data; don't log them. Run 1 of the probe printed an unmasked chatgptAccountId to scratch output. I deleted that file, fixed the masking, and none of the artifacts contain it.
- Side effect from this research: my read-only sqlite3 query of ~/.codex/thread_history_1.sqlite (WAL mode, no sidecar files at the time) created ~/.codex/thread_history_1.sqlite-wal (0 bytes) and ~/.codex/thread_history_1.sqlite-shm (32 KB) at 21:38. The database content is unchanged and this is the same idle state as goals_1/memories_1. I left them in place because deleting them could race with Codex opening the database. The user can delete them while no Codex process is running if desired. My probe runs also caused the normal Codex launch footprint (log rows, models_cache.json refresh, tmp/arg0). auth.json mtime stayed at Oct 5 15:37:38 throughout.
- Polling frequency limits on wham/usage are unknown. Codex's own clients poll it, but at an unknown rate. A 5-minute default plus a backoff after errors is prudent.

### Open questions

- What is the minimum codex CLI version that supports account/rateLimits/read with rateLimitsByLimitId and ordinaryUsageAllowed? Only 0.160.0 was tested; older Homebrew or npm installs may differ or lack the method.
- Where does Codex.app (the desktop app) bundle its CLI? /Applications/Codex.app/Contents/Resources/codex is a guess; the app is not installed here (only ~/Downloads/Codex.dmg).
- Would a long-lived app-server notice auth changes made by other Codex processes (logout, login, account switch)? The string 'Reloaded auth, changed:' suggests yes, but this was not tested; spawn-per-poll avoids the question.
- Could TokenBar use the app-server daemon (`codex app-server daemon start`, socket $CODEX_HOME/app-server-control/app-server-control.sock, or `codex app-server proxy`) instead of spawning? Framing and authentication on that socket were not tested, and no daemon was running.
- For users on keyring credential storage, the exact keychain key derivation (service 'Codex Auth', account 'cli|<hash of CODEX_HOME>') could not be checked without keychain access, which was out of bounds. It doesn't affect the app-server approach, only a direct-HTTP fallback.
- Which buckets appear in rateLimitsByLimitId / additional_rate_limits for other plans (Pro, Team, Business), for example 'premium' or per-model limits? Only 'codex' was seen live; 'premium' with null windows appeared in rollouts.
- Is resetsAt always about now + window when usedPercent is 0? Seen on 3 polls; worth re-checking after the window starts.
- What is the acceptable polling rate for wham/usage via the app-server, and does the backend rate-limit frequent usage reads?

### Recommended approach

Use the swift-smoke layout as the MVP skeleton:
- Package.swift: tools 6.2, macOS 14, Swift 6 mode.
- TokenBarCore: nonisolated. Holds Sendable models, file parsing, the ProcessRunner subprocess helper and any HTTP client. All usage-source logic goes here and is unit-tested with swift-testing via scripts/test.sh.
- tokenbar CLI: for debugging the usage readers headlessly, printing JSON.
- TokenBarApp: .defaultIsolation(MainActor.self). An @Observable model drives MenuBarExtra(.window) and a Settings scene.

Day-to-day commands (all set DEVELOPER_DIR to CLT): `swift build`, then `scripts/test.sh`, then `scripts/bundle.sh`, then `open dist/TokenBar.app`. Use `dist/TokenBar.app/Contents/MacOS/TokenBar --selftest` as an automated smoke test of the bundle. Keep bundle id dev.tokenbar.TokenBar fixed. For daily use, install a copy at ~/Applications/TokenBar.app.

UI patterns:
- Menu bar label: HStack { Image; Text } for icon plus percentage, or ImageRenderer to a template NSImage for per-account mini bars. Never a bare Label, which shows only the icon.
- Settings button: `NSApp.activate(ignoringOtherApps: true); openSettings()`.
- Refresh: a Task loop plus a didWake observer that hops with `Task { @MainActor in }`.

Subprocesses: resolve claude/codex to absolute paths once; the PATH of a Finder-launched app is minimal. Always pass a timeout.

Credentials: read them in Core. If a keychain item must be read, prefer running /usr/bin/security over SecItemCopyMatching, but only after another track confirms how the item was created (its ACL). Never log secrets. Never read under ~/Desktop, ~/Documents or ~/Downloads, which are TCC-protected and would re-prompt on every ad-hoc rebuild.

Defer to Settings toggles with user consent: launch at login via SMAppService.mainApp from ~/Applications, and notifications via UNUserNotificationCenter. Test both manually once on this MDM-managed Mac before relying on them. Keep app assets out of SwiftPM resources: use Contents/Resources plus Bundle.main.

### Findings

- **Toolchain: Xcode license / DEVELOPER_DIR** (high): Xcode 27.0 (27A266) is installed at /Applications/Xcode.app and xcode-select points to it, but its license has not been accepted. Every swift/xcrun call fails unless DEVELOPER_DIR=/Library/Developer/CommandLineTools. That variable is exported in ~/.zshenv:3, ~/.bashrc:6 and ~/.bash_profile:10, so interactive shells work. Anything that does not read those files (launchd jobs, some GUI tools) will fail. Both scripts default DEVELOPER_DIR to CLT. Running `sudo xcodebuild -license accept` would enable Xcode's toolchain and XCTest instead; that is the user's call.
- **Package configuration decision** (high): Use swift-tools-version 6.2, platforms .macOS(.v14), swiftLanguageModes [.v6]. Turn on .defaultIsolation(MainActor.self) for the TokenBarApp target only, and keep TokenBarCore nonisolated with Sendable models and async APIs. macOS 14 is required for @Observable, SettingsLink/@Environment(\.openSettings) and NSApp.activate(). Tools 6.2 is required for defaultIsolation. Tools 6.0 also works if @MainActor is written explicitly; that variant compiled cleanly on the first try.
- **Build commands and timings** (high): `swift build` and `swift build -c release` work with CLT only. Most of the clean-build time is building the SDK clang/Swift module cache: ModuleCache is 204 MB and .build is 444 MB in total. Release binaries: app about 450-487 KB, CLI 265 KB. The CLI prints valid pretty JSON.
- **Swift 6 strict concurrency: errors hit and fixes** (high): The project code produced 0 concurrency errors in Swift 6 mode, both with nonisolated default and with MainActor default isolation. The only compile error came from the test file: an array literal mixing (TimeInterval?, String) and (Int, String) tuples was inferred as [Any], which is not Sendable. Fix: a typed `static let resetCases: [(TimeInterval?, String)]`. A pitfall probe against the 26.2 SDK found:
- A global `var` is an error. Fix: let, an actor, or @MainActor.
- Capturing and mutating a `var data` in a readabilityHandler is an error. Fix: OSAllocatedUnfairLock<Data>, or Mutex on macOS 15+.
- A Timer block or addObserver(queue: .main) block calling an @MainActor method gives only a warning, because those APIs are @preconcurrency. Fix: `MainActor.assumeIsolated {}` or `Task { @MainActor in }`; both compile clean.
- Under defaultIsolation(MainActor), a Codable struct's conformance becomes MainActor-isolated and cannot be used in Task.detached or nonisolated code. Fix: keep models and parsers in the nonisolated Core module, or mark them `nonisolated`.
- Process, Pipe, DateFormatter and NotificationCenter.notifications(named:) under @MainActor caused no diagnostics.
- **Subprocess + async/await** (high): ProcessRunner.run works under Swift 6 without blocking any concurrency thread or the main actor. It is built from a continuation, readabilityHandler draining both pipes, a DispatchGroup that waits for exit plus EOF on both pipes, OSAllocatedUnfairLock buffers, withTaskCancellationHandler, and a GCD watchdog timeout. It is called from the app's MainActor on every refresh.
- **swift-testing with CLT only (no XCTest)** (high): swift-testing works, but plain `swift test` does not. Three command-line flags are needed, and scripts/test.sh adds them:
1. `-Xswiftc -F -Xswiftc /Library/Developer/CommandLineTools/Library/Developer/Frameworks`. Without it the Testing module is not found.
2. `-Xswiftc -Xfrontend -Xswiftc -disable-cross-import-overlays`. CLT 26.3 ships _Testing_Foundation.framework without its swiftmodule: Modules is a dangling symlink and Versions/A has only the binary, Resources and _CodeSignature.
3. `-Xlinker -rpath -Xlinker <same dir>`. Without it the test bundle fails to load Testing.framework at runtime.
Trap: if -F is set only via Package.swift unsafeFlags, `swift test` exits 0 having run 0 tests. SwiftPM's generated runner.swift wraps the entry point in `#if canImport(Testing)`, and that target sees only command-line flags. test.sh therefore fails when no 'Test run with N>0 tests' line appears, and uses --scratch-path .build-tests so the extra flags do not invalidate .build/.
- **Bundling and ad-hoc signing** (high): scripts/bundle.sh builds the release TokenBarApp product, copies it to dist/TokenBar.app/Contents/MacOS/TokenBar, and writes Info.plist with 14 keys (including LSUIElement, LSMinimumSystemVersion 14.0 and NSHighResolutionCapable), PkgInfo and Resources. It then runs plutil -lint and `codesign --force --sign - --timestamp=none`, followed by a strict verify. It takes about 3.5 s after a release build. Gatekeeper rejecting the app is expected and does not matter for a locally built app, which carries no quarantine xattr.
- **Launch via open, accessory status, quit** (high): `open dist/TokenBar.app` starts the app. It is alive after 3 s and registered as a UIElement accessory app, so there is no Dock icon. SIGTERM (pkill/kill) ends it immediately but skips applicationWillTerminate. NSApp.terminate (the Quit button, or the self-test) exits gracefully. Running the bundle binary directly also works and returns an exit code, which suits CI. No crash happened.
- **Idle resource use** (high): While idle, the app uses about 0% CPU, a 17 MB physical footprint (the number Activity Monitor shows), about 76-79 MB RSS (mostly shared system framework pages), 4-6 threads, 0 idle wakeups and an energy impact of 0.0.
- **MenuBarExtra label rendering (macOS 26.7)** (high): How the label view maps onto NSStatusBarButton:
- `HStack { Image(systemName:); Text }`: icon and text. This is the default in the App file.
- `Label(text, systemImage:)`: icon only; the text is dropped.
- `Text("\(Image(systemName:)) 43%")`: the symbol becomes an inline text attachment.
- ImageRenderer to a template NSImage: any custom drawing, e.g. one mini bar per account.
- **Settings scene from an LSUIElement MenuBarExtra app** (high): Findings on opening Settings:
- `NSApp.sendAction(Selector(("showSettingsWindow:")), to: nil, from: nil)` returns true but does nothing on macOS 14+.
- openSettings() without activation opens Settings behind other apps: occluded and not key.
- Cooperative NSApp.activate() was refused when Settings was opened programmatically.
- `NSApp.activate(ignoringOtherApps: true)` followed by openSettings() made the app active and Settings visible and key. No deprecation warning appears with the 26.2 SDK. This is what the App file ships.
- SettingsLink compiles, but it cannot activate the app first.
Not tested: whether a real user click lets cooperative activate() succeed.
- **Periodic refresh and wake handling** (high): A Task-based loop (`Task.sleep(for:tolerance:)` on ContinuousClock, restarted when the interval changes) and an NSWorkspace.didWakeNotification observer that hops to MainActor both work. Only a synthetic wake notification was tested, not a real system sleep/wake.
- **Environment of a GUI-launched app (PATH)** (medium): Launched via `open` from the agent's shell, the app inherited the shell's PATH, including ~/.nvm/versions/node/v20.20.2/bin. When launched from Finder, Dock or a login item it gets launchd's minimal PATH (/usr/bin:/bin:/usr/sbin:/sbin). The MVP should run claude/codex by resolved absolute path and never rely on PATH. Unrelated noise: PATH also contains Apple's '/var/run/com.apple.security.cryptexd/codex.system/...', a cryptex that has nothing to do with OpenAI Codex.
- **Product naming on case-insensitive APFS** (high): The root volume is case-insensitive, so an app product named 'TokenBar' and the CLI product 'tokenbar' would overwrite each other in .build/<config>/. The app product is therefore TokenBarApp, and the bundling script renames the binary to Contents/MacOS/TokenBar.
- **SwiftPM resources inside a hand-built .app** (high): SwiftPM 6.2.4's generated Bundle.module looks in only two places: Bundle.main.bundleURL/<Pkg>_<Target>.bundle (the .app root, where codesign rejects unsealed content) and the absolute .build path. The second works on the dev machine until .build is deleted, then crashes. Do not use SwiftPM `resources:` for the app target. Put assets in ./Resources, have bundle.sh copy them to Contents/Resources, and load them with Bundle.main. Use SF Symbols for icons where possible.
- **Side effect under ~/Library** (high): Launching the app caused cfprefsd to create ~/Library/Preferences/dev.tokenbar.TokenBar.plist. It holds only the Settings window-frame autosave, written by the self-test runs that opened Settings. CFFIXED_USER_HOME passed with `open --env` did not redirect it. Permission is tracked per bundle ID by usernoted, not per code signature, so it should survive rebuilds if CFBundleIdentifier stays fixed (medium confidence).

Install a copy at a stable path first (~/Applications/TokenBar.app needs no admin). Drive a Settings toggle from SMAppService.mainApp.status, and handle .requiresApproval with SMAppService.openSystemSettingsLoginItems().

- **Reading another app's keychain item (knowledge; keychain never touched)** (medium): Items in the file-based login keychain carry an ACL listing trusted apps, which by default includes the creating app, plus a partition list (apple-tool:, apple:, teamid:...).

- The data-protection keychain needs keychain-access-groups entitlements, which ad-hoc signing cannot provide.
- Never put secrets in command-line arguments, and never log them.
- **Runtime log noise** (high): The only framework messages at launch are harmless App Intents (linkd) registration failures, expected for an unregistered ad-hoc app, plus the SettingsLink hint. `log show` cannot run inside the agent sandbox ('Could not open local log store: Operation not permitted'). ### Risks

- Builds depend on DEVELOPER_DIR=/Library/Developer/CommandLineTools because Xcode 27 is installed but unlicensed. Any context that does not read ~/.zshenv, ~/.bashrc or ~/.bash_profile (launchd jobs, some GUI editors) gets exit 69. Updating CLT or Xcode, or accepting the license, could also change the toolchain or swift-testing packaging under us.
- The swift-testing workaround depends on a CLT packaging defect (_Testing_Foundation shipped without a swiftmodule). It may change in a future CLT. Anyone who moves the -F flag into Package.swift gets a silent '0 tests, exit 0'. scripts/test.sh guards against that, but plain `swift test` does not.
- Every ad-hoc rebuild changes the code-signing identity (cdhash). Any TCC grant (Desktop/Documents folder access, Accessibility, Screen Recording) or keychain 'Always Allow' given to TokenBar will prompt again after each rebuild. Design the app to need none of them.
- NSApp.activate(ignoringOtherApps:) is deprecated since macOS 14. It works on 26.7, but a future macOS may make it cooperative-only, and Settings would then open behind other windows.
- The self-test relies on private class names and identifiers (NSStatusBarWindow, MenuBarExtraWindow, com_apple_SwiftUI_Settings_window). They may change between OS releases. This affects test code only.
- This is a Jamf-managed Mac with Microsoft Defender, Citrix, and MDM payloads for servicemanagement, loginitems.managed, notificationsettings, systempolicy.control and TCC PPPC. Today the ad-hoc app launches fine, but a policy change could block unsigned apps, login items or notifications.
- Shelling out to claude/codex from the GUI app breaks if it relies on PATH, which is minimal outside a shell. The nvm path is node-version-specific (v20.20.2), so it changes when node is upgraded.
- SIGTERM (pkill) skips applicationWillTerminate, so any cached state must be saved as it changes, not at quit.
- SwiftPM Bundle.module resources look fine on the dev machine (absolute .build path) but crash once .build is deleted or the app is moved.
- Launching the app writes to ~/Library/Preferences/dev.tokenbar.TokenBar.plist (window frame). It may also add an entry to macOS 26's 'Allow in the Menu Bar' list in System Settings (not inspected). If the user hides the status item, the app has no UI; adding applicationShouldHandleReopen to open Settings would help.
